# Лабораторная работа №3 — серверный каркас

Тема: создание базового каркаса приложения, Clean / Layered Architecture и настройка окружения.

Предметная область: информационная система управления заказами и товарными запасами цветочного магазина с интерактивным конструктором букетов.

Источник требований — `Lab#03_Clean_Layered_Architecture.pdf`, 5 страниц, из [папки лабораторных работ](https://drive.google.com/drive/folders/1fwY7O8OnPeHtRFqjpxeAQ4JUWXz45qph). В этой работе требуется инициализировать серверный проект, разделить код на слои, настроить конфигурацию, реализовать health-check и показать его локальную работу.

## Результат и границы работы

Используется ранее выбранный Python + FastAPI. Реализован `GET /api/v1/health`: публичный JSON-ответ `200 OK` со статусом `pass`, названием, версией, окружением и временем работы сервиса. Health-check подтверждает, что HTTP-процесс принимает запросы. Проверка подключения к БД здесь не выполняется: подключение PostgreSQL относится к следующему этапу.

Проектный `openapi.yaml` сохраняет контракт лабораторной №2 и дополнен health-check. Автоматический `/openapi.json` работающего FastAPI описывает реализованные маршруты. Эти документы имеют разные задачи: проектный контракт задает план системы, а схема работающего сервера — доступные сейчас операции.

## Структура

```text
src/flower_shop/
├── __main__.py       # Запуск с учетом HTTP_HOST и HTTP_PORT
├── main.py           # Создание приложения и связывание зависимостей
├── api/              # HTTP-маршруты и схемы транспорта
├── service/          # Сервисы и данные, независимые от HTTP
├── repository/       # Граница будущего доступа к данным
└── config/           # Чтение и валидация настроек
tests/                # Проверки каркаса и конфигурации
.env.example          # Общий шаблон настроек
pyproject.toml        # Описание Python-пакета
requirements.txt      # Зависимости запуска
requirements-dev.txt  # Зависимости разработки и тестов
```

`main.py` выступает точкой сборки зависимостей: создает приложение и передает настроенный сервис HTTP-слою. Контроллер принимает HTTP-запрос, обращается к сервису и возвращает ответ. Сервис не импортирует FastAPI и не знает о заголовках, статусах HTTP или сериализации JSON. Настройки поступают в сервис как значения, а не читаются им из `.env`.

Для health-check репозиторий не нужен: необходимые данные находятся в памяти процесса. Каталог `repository` выделен для будущих адаптеров хранения, без фиктивных SQL-запросов. Когда появятся сценарии заказов и запасов, сервисы будут обращаться к интерфейсам репозиториев, а конкретные реализации будут передаваться в точке сборки. Это сохраняет направление зависимостей и позволяет заменить хранилище без переписывания бизнес-правил.

## Конфигурация окружения

`.env.example` описывает `APP_NAME`, `APP_VERSION`, `APP_ENV`, `HTTP_HOST` и `HTTP_PORT`. Локальная копия `.env` считывается из рабочего каталога при запуске. Значения из окружения процесса имеют более высокий приоритет. Конфигурация валидируется до обслуживания запросов: неправильный порт, пустое обязательное значение или недопустимое окружение должны приводить к явной ошибке запуска.

Секреты будущих подключений не добавляются в исходники или ответы health-check. `.env` находится в `.gitignore`; `.env.example` отслеживается Git и содержит только безопасные примеры.

## Health-check

| Свойство | Значение |
|---|---|
| Метод и маршрут | `GET /api/v1/health` |
| Авторизация | Не требуется |
| Успешный статус | `200 OK` |
| Формат ответа | `application/json` |
| `status` | `pass` |
| `app_name` | Название из конфигурации |
| `version` | Версия из конфигурации |
| `environment` | Окружение из конфигурации |
| `uptime` | Неотрицательное число секунд с начала работы |

Время работы измеряется монотонными часами, поэтому перевод системного времени не уменьшает uptime. После перезапуска процесса отсчет начинается заново. При запуске нескольких процессов значение относится к тому процессу, который обработал запрос.

Команды установки, запуска и проверки находятся в [README](../README.md#запуск-сервера--лабораторная-3). Для демонстрации через браузер достаточно открыть `http://127.0.0.1:8000/api/v1/health` после запуска приложения.

## Соответствие методичке

| Требование | Реализация или материал для показа |
|---|---|
| Инициализация проекта на выбранном языке | Python-пакет `src/flower_shop`, `pyproject.toml`, файлы зависимостей |
| Разделение по слоям | Каталоги `api`, `service`, `repository`, точка сборки `main.py` |
| Чтение конфигурации окружения | Модуль `config`, переменные процесса и `.env` |
| Health-check с HTTP 200 и базовой информацией | `GET /api/v1/health` |
| Название, версия и uptime | Поля `app_name`, `version`, `uptime` в JSON |
| Шаблон конфигурации без секретов | `.env.example` |
| Исключение локальных файлов | `.gitignore`: `.env`, `.venv`, Python-кэш и результаты сборки |
| Демонстрация локального запуска | Команды README, браузер или `curl.exe -i` |
| Контрольные вопросы | [Пять ответов](control-questions-lab3.md) |
| Git-репозиторий с исходниками | Ветка лабораторной и PR в репозитории проекта |

Docker, миграции PostgreSQL, CRUD заказов и авторизация не являются требованиями этой лабораторной работы.
