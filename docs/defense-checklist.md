# Защита лабораторных №1–3

## Лабораторная №1

1. Открыть README и назвать тему и назначение системы.
2. В ARCHITECTURE показать роли и шесть основных Use Cases; подробности находятся в docs/use-cases.md.
3. Показать C4 Container и объяснить взаимодействие веб-клиента, Backend API и хранилищ.
4. Открыть docs/diagrams/erd.svg отдельно с увеличением: 17 таблиц, 23 связи. Исходник схемы — erd.dbml.
5. Объяснить PK/FK, уникальность, проверки и индексы. Пример N:M: recipes → recipe_items ← products; роли пользователя связаны через user_roles.
6. Объяснить 3NF, исторические снимки цены и названия; показать, что line_total, subtotal и total рассчитываются для API и не дублируются в таблицах (docs/domain-model.md).
7. Подготовить ответы из docs/control-questions.md.

## Лабораторная №2

1. Выполнить npm ci, затем npm run validate.
2. Показать раздел REST API Specs в ARCHITECTURE и openapi.yaml: 22 бизнес-операции из лабораторной №2 и добавленный в лабораторной №3 health-check, всего 23 операции.
3. Запустить python -m http.server 8080 --bind 127.0.0.1 и открыть http://127.0.0.1:8080/docs/swagger-ui.html.
4. Развернуть POST /auth/login, GET /products, POST /orders и PATCH позиции букета; показать схемы запросов, ответов, ошибки и JWT.
5. Объяснить 401/403/404/409, отличие GET/POST/PATCH/DELETE и Query/Path/Body.
6. Ответы на все пять вопросов — docs/control-questions-lab2.md.

Статическая страница Swagger UI визуализирует полный контракт и не отправляет запросы. Фактическое выполнение бизнес-операций будет реализовано на следующих этапах.

## Лабораторная №3

1. Открыть дерево `src/flower_shop`: показать `api`, `service`, `repository`, `config`, точку сборки `main.py` и запуск `__main__.py`.
2. Показать, что контроллер вызывает сервис, а сервис не зависит от HTTP и FastAPI. Объяснить, почему health-check не требует репозитория или подключения к БД.
3. Открыть `.env.example` и `.gitignore`. Выполнить `git ls-files .env .env.example`: в отслеживаемых файлах должен быть только `.env.example`.
4. Установить зависимости и запустить приложение по разделу README «Запуск сервера — лабораторная №3».
5. Открыть `http://127.0.0.1:8000/api/v1/health` или выполнить `curl.exe -i http://127.0.0.1:8000/api/v1/health`. Показать `200 OK`, `application/json`, название, версию, окружение и uptime.
6. Через несколько секунд повторить запрос и показать рост uptime. При необходимости изменить `APP_NAME` в локальном `.env`, перезапустить процесс и показать новое название. После демонстрации восстановить свое значение.
7. Открыть `http://127.0.0.1:8000/docs`: это Swagger UI реализованного сервера с health-check, в отличие от полного проектного контракта на статическом порту `8080`.
8. Выполнить `.\.venv\Scripts\python.exe -m pytest` и подготовить ответы из `docs/control-questions-lab3.md`.

Подробное соответствие требованиям находится в [lab3.md](lab3.md). Рабочий серверный каркас выполняет health-check; заказы, каталог, авторизация и база данных на этом этапе еще не реализованы.
