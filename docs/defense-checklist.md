# Защита лабораторных №1–4

[Вернуться в README](../README.md) · [Что говорить и как объяснять код](defense-guide.md)

## До начала демонстрации

1. Открыть README нужной версии репозитория. На GitHub выбрать ветку, в которую вошли подготовленные материалы; перед сдачей убедиться, что нужный PR объединен с `main`.
2. Заранее установить зависимости по README и проверить `npm run validate` и `.\.venv\Scripts\python.exe -m pytest`. Не оставлять скачивание пакетов и базового образа на время ответа.
3. Запустить статическую документацию на `8080` и локальный backend на `8000` в двух отдельных терминалах. Для ЛР4 проверить Docker Engine и запустить контейнер на `8081` по README. Уже работающие экземпляры повторно не запускать.
4. Проверить health на `8000` и `8081`. Для Swagger работающего FastAPI нужен доступ к CDN; при его отсутствии показать JSON через `curl.exe -i`. Статический Swagger после `npm ci` использует локальные ресурсы.
5. Держать открытыми C4, ERD, `openapi.yaml`, `src/flower_shop/main.py` и `Dockerfile`. Показать разные результаты лабораторных по порядку ниже.

## Лабораторная №1

1. Открыть README и назвать тему и назначение системы.
2. В ARCHITECTURE показать роли и шесть основных Use Cases; подробности находятся в docs/use-cases.md.
3. Показать C4 Container и объяснить взаимодействие веб-клиента, Backend API и хранилищ.
4. Открыть docs/diagrams/erd.svg отдельно с увеличением: 17 таблиц, 23 связи. Исходник схемы — erd.dbml.
5. Объяснить PK/FK, уникальность, проверки и индексы. Пример N:M: bouquet_recipes → recipe_items ← products; роли пользователя связаны через user_roles.
6. Объяснить 3NF, исторические снимки цены и названия; показать, что line_total, subtotal и total рассчитываются для API и не дублируются в таблицах (docs/domain-model.md).
7. Подготовить ответы из docs/control-questions.md.

## Лабораторная №2

1. Выполнить npm ci, затем npm run validate.
2. Показать раздел REST API Specs в ARCHITECTURE и openapi.yaml: 22 бизнес-операции из лабораторной №2 и добавленный в лабораторной №3 health-check, всего 23 операции.
3. Запустить python -m http.server 8080 --bind 127.0.0.1 и открыть http://127.0.0.1:8080/docs/swagger-ui.html.
4. Развернуть POST /auth/login, GET /products, POST /orders и PATCH позиции букета; показать схемы запросов, ответов, ошибки и JWT.
5. Объяснить 401/403/404/409, отличие GET/POST/PATCH/DELETE и Query/Path/Body.
6. Ответы на все пять вопросов — docs/control-questions-lab2.md.

Статическая страница Swagger UI визуализирует полный контракт и не отправляет запросы. Фактическое выполнение бизнес-операций будет реализовано на следующих этапах.

## Лабораторная №3

1. Открыть дерево `src/flower_shop`: показать `api`, `service`, `repository`, `config`, точку сборки `main.py` и запуск `__main__.py`.
2. Показать, что контроллер вызывает сервис, а сервис не зависит от HTTP и FastAPI. Объяснить, почему health-check не требует репозитория или подключения к БД.
3. Открыть `.env.example` и `.gitignore`. Выполнить `git ls-files .env .env.example`: в отслеживаемых файлах должен быть только `.env.example`.
4. Установить зависимости и запустить приложение по разделу README «Запуск сервера — лабораторная №3».
5. Открыть `http://127.0.0.1:8000/api/v1/health` или выполнить `curl.exe -i http://127.0.0.1:8000/api/v1/health`. Показать `200 OK`, `application/json`, название, версию, окружение и uptime.
6. Через несколько секунд повторить запрос и показать рост uptime. При необходимости изменить `APP_NAME` в локальном `.env`, перезапустить процесс и показать новое название. После демонстрации восстановить свое значение.
7. Открыть `http://127.0.0.1:8000/docs`: это Swagger UI реализованного сервера с health-check, в отличие от полного проектного контракта на статическом порту `8080`.
8. Выполнить `.\.venv\Scripts\python.exe -m pytest` и подготовить ответы из `docs/control-questions-lab3.md`.

Подробное соответствие требованиям находится в [lab3.md](lab3.md). Рабочий серверный каркас выполняет health-check; заказы, каталог, авторизация и база данных на этом этапе еще не реализованы.

## Лабораторная №4

1. Убедиться, что Docker Engine запущен для Linux-контейнеров: выполнить `docker info`.
2. Показать корневые `Dockerfile` и `.dockerignore`. Объяснить стадии builder/runtime, исключение `.env`, тестов и локальных зависимостей, порядок слоев кэша и запуск без root.
3. Из корня проекта выполнить `docker build -t flower-shop-api:lab4 .`. Показать успешный результат сборки и `docker images flower-shop-api`.
4. Выполнить `docker run --name flower-shop-lab4 -d -p 127.0.0.1:8081:8000 -e APP_ENV=development -e "APP_NAME=Flower Shop API (Docker)" flower-shop-api:lab4`. Если такое имя уже используется вашим предыдущим учебным контейнером, сначала проверить его и выполнить остановку/удаление по шагу 8.
5. Показать `docker ps --filter name=flower-shop-lab4` и `docker logs flower-shop-lab4`.
6. Открыть `http://127.0.0.1:8081/api/v1/health` или вызвать `curl.exe -i` по этому адресу. Показать HTTP 200, имя с пометкой `(Docker)`, окружение `development` и uptime.
7. Показать проверку через `docker exec` из [lab4.md](lab4.md) и `docker inspect --format '{{.State.Health.Status}}' flower-shop-lab4`: после успешного HEALTHCHECK ожидается `healthy`.
8. Выполнить `docker stop flower-shop-lab4`, затем `docker rm flower-shop-lab4`; объяснить, почему образ при этом сохраняется.
9. Подготовить пять ответов из [control-questions-lab4.md](control-questions-lab4.md), особенно отличие `EXPOSE` от публикации `-p` и причину `HTTP_HOST=0.0.0.0` внутри контейнера.

База данных и Docker Compose относятся к следующим лабораторным. При сдаче требуется показать реальные сборку и запуск: один Dockerfile без работающего контейнера не закрывает практическую часть.
