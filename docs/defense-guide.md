# Как объяснить проект на защите лабораторных №1–4

[README и запуск](../README.md) · [Чек-лист показа](defense-checklist.md) · [Результаты проверок](validation-report.md)

## Вступление

Тема проекта — «Разработка информационной системы управления заказами и товарными запасами цветочного магазина с интерактивным конструктором букетов».

Короткое объяснение:

> Система предназначена для выбора состава букета, расчета цены, оформления заказа и учета необходимых товаров. Лабораторные последовательно готовят такую систему: сначала архитектуру и данные, затем API-контракт, работающий серверный каркас и его Docker-образ. На текущем этапе исполняется проверка здоровья сервера. Бизнес-сценарии магазина спроектированы и будут реализовываться далее.

Сразу откройте таблицу четырех лабораторных в README. После этого показывайте результаты в следующем порядке.

## Лабораторная №1: зачем нужна система и как устроены данные

**Открыть:** [ARCHITECTURE.md](../ARCHITECTURE.md), [C4](diagrams/c4-container.svg), [ERD](diagrams/erd.svg) и [Use Cases](use-cases.md).

**Объяснить:**

> Клиент собирает букет и оформляет заказ. Менеджер проверяет заказ, кладовщик учитывает товары, флорист собирает букет, администратор управляет доступом. Выбран модульный монолит: один backend с отдельными модулями, чтобы упростить разработку и согласованные операции заказа и склада.

На C4 покажите пользователей, веб-приложение, API и хранилища. Объясните, что C4 Container обозначает приложение или хранилище как архитектурную единицу. Он не означает, что все нарисованные части уже запущены как Docker-контейнеры. Vue, PostgreSQL, Redis, хранилище изображений и уведомления пока относятся к целевой архитектуре.

На ERD пройдите один сценарий:

1. `products` содержит цветы, упаковку и другие компоненты; `categories` группирует товары.
2. `bouquet_recipes` и `recipe_items` описывают шаблоны. `bouquet_drafts` и `bouquet_draft_items` — изменяемый состав клиента.
3. `orders` хранит заказ, `order_items` — его строки, `order_status_history` — историю статусов.
4. `stock_balances` хранит физический остаток и агрегат резервов по товару и складу. `reservations` содержит резервы, `stock_movements` — журнал операций.

Пример для объяснения, **не результат работающей складской операции**: на складе 20 роз, 5 зарезервировано, доступно 15. Заказ на 7 роз увеличит резерв до 12; физический остаток пока останется 20, доступно будет 8. При начале сборки эти 7 роз спишутся, их резерв закроется: физически 13, зарезервировано 5, доступно 8. Эти изменения должны выполняться транзакционно. Подробности — в [бизнес-правилах](business-rules.md).

Три понятных примера связей:

- `categories → products` — 1:N: одна категория содержит несколько товаров.
- `bouquet_recipes → recipe_items ← products` — N:M: рецепт содержит несколько товаров, товар участвует в разных рецептах.
- `users → customer_profiles` — 1:0..1: пользователь может иметь один профиль клиента; он не обязателен для сотрудника.

Для вопроса о 3NF: состав заказа хранится отдельными строками, справочники связаны ключами, повторяющихся столбцов «цветок1/цветок2» нет. Цена и название в строке заказа — исторический снимок; изменение каталога не меняет прошлую продажу. `line_total`, `subtotal` и `total` вычисляются для ответа API, а не хранятся в таблицах. `stock_balances.reserved` — осознанный агрегат активных резервов; его согласованность должна обеспечиваться транзакциями.

**Итог работы:** модель и схемы на 17 таблиц и 23 связи. DBML еще не является выполненной миграцией БД. [Ответы на контрольные вопросы №1](control-questions.md).

## Лабораторная №2: как клиент общается с сервером

**Открыть:** [openapi.yaml](../openapi.yaml), таблицу REST API Specs в [ARCHITECTURE.md](../ARCHITECTURE.md) и статический Swagger `http://127.0.0.1:8080/docs/swagger-ui.html` после запуска по README.

**Объяснить:**

> Контракт задает методы, адреса, параметры, JSON-запросы, ответы и ошибки до реализации бизнес-функций. Здесь 22 бизнес-операции для авторизации, каталога, букетов, заказов и склада. Позже добавлен реализованный health-check, поэтому сейчас в полном контракте 23 операции.

Покажите три примера:

| Что раскрыть в Swagger | Как объяснить |
|---|---|
| `GET /products` | Чтение каталога; фильтры идут в query-параметрах, просмотр активного каталога публичный |
| `POST /orders` | Создание заказа; состав запроса передается JSON-телом; контракт описывает успешный ответ 201 и конфликт 409 |
| `PATCH /bouquet-drafts/{draftId}/items/{itemId}` | Изменение позиции; UUID в path выбирают конкретный черновик и строку, новое количество передается в body |

В YAML пути указаны относительно `servers.url: /api/v1`. Поэтому проектный `/orders` соответствует полному адресу `/api/v1/orders`. Схемы в `components/schemas` повторно используются через `$ref`.

JWT описывает будущую авторизацию: 401 — нет действительного токена, 403 — недостаточно прав, 404 — ресурс отсутствует или скрыт от чужого пользователя, 409 — конфликт состояния или нехватка товара. Наличие описания JWT не означает, что вход уже реализован.

**Итог работы:** спецификация OpenAPI 3.0.3 и просмотр ее схем. Отправка запросов в статическом Swagger отключена. Работающий FastAPI предоставляет отдельную автосхему OpenAPI 3.1 только для health-check. [Ответы на контрольные вопросы №2](control-questions-lab2.md).

## Лабораторная №3: как проходит реальный HTTP-запрос

**Открыть:** каталог `src/flower_shop`, перечисленные ниже файлы и `http://127.0.0.1:8000/docs` после запуска по README.

**Объяснить:**

> Сервер запускается командой `python -m flower_shop`. Точка запуска читает конфигурацию и запускает Uvicorn. Фабрика приложения создает FastAPI, подключает маршруты и создает health-сервис при старте. HTTP-обработчик получает сервис через зависимость FastAPI, вызывает его и возвращает типизированный JSON.

Откройте код в таком порядке:

| Файл | Что показать |
|---|---|
| [__main__.py](../src/flower_shop/__main__.py) | Функция `main`: `Settings()`, `create_app(settings)`, `uvicorn.run` с host и port |
| [config/settings.py](../src/flower_shop/config/settings.py) | `Settings` читает `.env` и окружение; проверяет обязательность строк, окружение и порт 1–65535 |
| [main.py](../src/flower_shop/main.py) | `create_app`, `lifespan`, создание `HealthService`, хранение в `app.state`, `include_router` |
| [api/health.py](../src/flower_shop/api/health.py) | Префикс `/api/v1`, маршрут `/health`, `Depends(get_health_service)`, вызов `service.get_health()` |
| [service/health.py](../src/flower_shop/service/health.py) | Формирование `HealthSnapshot`; `monotonic` для времени работы, отсутствие импорта FastAPI |
| [api/schemas.py](../src/flower_shop/api/schemas.py) | `HealthResponse` описывает поля JSON и ограничения ответа |
| [repository/__init__.py](../src/flower_shop/repository/__init__.py) | Граница будущего хранения данных; SQL и репозиторий пока не реализованы |

Реальный поток: `Uvicorn → FastAPI → api.health → HealthService → HealthSnapshot → HealthResponse → JSON`. Сервис не знает HTTP, а контроллер отвечает за представление ответа. Вызов `Depends` передает объект обработчику; это механизм внедрения зависимостей. Полноценного сервиса заказа и абстракции его репозитория в текущей реализации еще нет.

В Swagger нажмите Try it out → Execute для `GET /api/v1/health`. Альтернатива в другом терминале:

```powershell
curl.exe -i http://127.0.0.1:8000/api/v1/health
```

Покажите `200 OK`, `application/json` и поля `status`, `app_name`, `version`, `environment`, `uptime`. Повторите запрос через несколько секунд: uptime должен вырасти. Монотонные часы нужны, чтобы изменение календарного времени компьютера не исказило длительность работы.

Покажите [.env.example](../.env.example) и [.gitignore](../.gitignore). Шаблон содержит безопасные настройки, локальный `.env` игнорируется Git; переменные процесса имеют приоритет над файлом. Неверные настройки останавливают запуск до открытия порта. Для демонстрации изменения имени достаточно изменить `APP_NAME` в своем `.env` и перезапустить локальный сервер; после показа верните исходное значение.

Тесты: [test_health.py](../tests/test_health.py) проверяет ответ и uptime; [test_settings.py](../tests/test_settings.py) — конфигурацию; [test_architecture.py](../tests/test_architecture.py) — независимость сервисного слоя от внешних деталей. Команда: `.\.venv\Scripts\python.exe -m pytest`. Сейчас проверяется 19 случаев; известное предупреждение тестового адаптера Starlette описано в отчете.

**Итог работы:** работающий серверный каркас и один публичный бизнес-независимый маршрут. Health подтверждает жизнь процесса, готовность базы или оформления заказа он не проверяет. [Ответы на контрольные вопросы №3](control-questions-lab3.md).

## Лабораторная №4: как тот же сервер запускается в Docker

**Открыть:** [Dockerfile](../Dockerfile), [.dockerignore](../.dockerignore), [команды ЛР4](lab4.md) и Docker-терминал.

**Объяснить:**

> Образ упаковывает Python, зависимости и пакет сервера. Стадия builder создает виртуальное окружение и устанавливает пакет, стадия runtime получает это окружение и запускает приложение от обычного пользователя. Это тот же сервер, что в третьей лабораторной, с другим способом запуска.

Покажите инструкции Dockerfile сверху вниз:

| Инструкция | Зачем она нужна здесь |
|---|---|
| `FROM ... AS builder` и `FROM ... AS runtime` | Разделяют сборку пакета и его исполнение; основа — Python 3.13 slim |
| `COPY requirements.txt` перед `COPY src/` | Изменение исходников позволяет сохранить кэш установки зависимостей |
| `COPY --from=builder /opt/venv /opt/venv` | Переносит готовое окружение в финальную стадию |
| `ENV HTTP_HOST=0.0.0.0` | Сервер слушает интерфейсы внутри контейнера, доступные через публикацию порта |
| `USER 10001:10001` | Запускает сервер без root |
| `EXPOSE 8000` | Описывает внутренний порт; сам по себе наружу его не открывает |
| `HEALTHCHECK` | Периодически проверяет HTTP-ответ и `status=pass` средствами Python |
| `CMD ["python", "-m", "flower_shop"]` | Задает команду запуска; Python получает сигналы остановки как основной процесс |

`.dockerignore` разрешает передавать builder только манифесты и `src/`, исключая локальные зависимости, тесты, `.env`, Git и документацию. `.gitignore` на контекст Docker не влияет.

Команды сборки, запуска и очистки копируйте из [lab4.md](lab4.md). В публикации `127.0.0.1:8081:8000` первые адрес и порт относятся к компьютеру, последний порт — к контейнеру. Через `-e` передаются `APP_ENV` и `APP_NAME`; метка `(Docker)` в ответе помогает отличить этот экземпляр от локального на 8000.

Покажите `docker ps`, `docker logs`, HTTP 200 на `8081` и `docker inspect --format '{{.State.Health.Status}}' flower-shop-lab4`. Сразу после запуска статус может быть `starting`; после проверки ожидается `healthy`. Затем остановите и удалите только свой учебный контейнер по инструкции. Образ останется и позволит создать контейнер снова. Образ — сохраненный шаблон, контейнер — конкретный экземпляр его запуска.

**Итог работы:** реально собранный и проверенный контейнер сервера. База и Compose пока не подключены. [Ответы на контрольные вопросы №4](control-questions-lab4.md).

## Если демонстрация не идет по плану

| Наблюдение | Что проверить или объяснить |
|---|---|
| В Swagger виден только health | На 8000 и 8081 это правильно. Для полного контракта открыть статический Swagger на 8080 |
| Каталог или заказ возвращает 404 | Эти операции еще не реализованы; показать их схемы в проектном YAML |
| Страница FastAPI `/docs` пустая без интернета | Ресурсы Swagger идут из CDN. Показать фактический health через `curl.exe -i`; полный контракт доступен в локальном статическом Swagger после `npm ci` |
| Подключение отклонено на 8000 или 8080 | Проверить нужный терминал, запуск из корня и host/port в конфигурации; адрес сам по себе сервер не запускает |
| Имя Docker-контейнера занято | Посмотреть `docker ps -a --filter name=flower-shop-lab4`. Работающий экземпляр можно демонстрировать; остановленный свой экземпляр можно запустить через `docker start flower-shop-lab4` |
| Docker Engine недоступен | Проверить `docker info` и запуск Linux-движка Desktop. Проверки прошлой сборки есть в отчете, но они не заменяют текущую практическую демонстрацию |
| Конструктор не открывается как сайт | В ЛР1–4 подготовлены его сценарии, модель и контракт; пользовательский интерфейс еще не реализован |

## Что должно остаться понятным после ответа

Преподавателю можно показать связь всех четырех работ: требования магазина определяют модель данных; модель и сценарии определяют API; серверный каркас задает место будущей реализации; Docker воспроизводит запуск этого каркаса. Проверки подтверждают текущий этап, а ограничения перечислены рядом с его результатами.

Перед сдачей пройдите [короткий чек-лист](defense-checklist.md) и прочитайте контрольные вопросы к нужной работе. Команды установки и запуска остаются в [README](../README.md), чтобы их можно было повторить из одного источника.
