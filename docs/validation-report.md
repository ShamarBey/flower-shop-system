В лабораторной №3 еще не подключены СУБД, миграции, авторизация, каталог и заказы. Отсутствующие серверные операции возвращают 404. Это соответствует границам каркаса из методички.

## Контейнеризация — лабораторная №4

Проверено на Docker Desktop 4.73.0, Docker Engine 29.4.3, контекст `desktop-linux`, Linux/amd64. Требования сверены со всеми пятью страницами `Lab#04_Docker.pdf`.

| Проверка | Фактический результат |
|---|---|
| Dockerfile | `docker build --check .` завершился успешно, предупреждений нет |
| Чистая локальная сборка | `docker build -t flower-shop-api:lab4 .` скачал Python slim, установил зависимости и пакет приложения, создал образ |
| Кэш | Повторная сборка использовала `CACHED` для установки зависимостей, приложения и runtime-слоев |
| Образ | `flower-shop-api:lab4`, ID после повторной сборки `e1ed76084613`; `docker images` показал 219 MB |
| Контекст | Первая передача исходников — 8.10 kB; используется allowlist `.dockerignore`, исключены `.env`, Git, тесты и локальные зависимости |
| Запуск | `flower-shop-lab4`, опубликован только `127.0.0.1:8081 → 8000/tcp` |
| Настройки | Через `-e` переданы `APP_ENV=development` и `APP_NAME=Flower Shop API (Docker)`; значения подтверждены ответом сервера |
| HTTP с компьютера | `curl.exe -i http://127.0.0.1:8081/api/v1/health`: `200 OK`, `application/json`, все пять полей; uptime растет |
| HTTP из контейнера | `docker exec` с `urllib.request` получил 200 и проверил `status`, `app_name`, `environment` |
| Встроенный HEALTHCHECK | `docker inspect` показал `running healthy` |
| Пользователь и состав | `os.getuid()` вернул 10001; `/app` пуст, `/build` отсутствует, `pytest` не установлен; пакет запускается из `/opt/venv` |
| Зависимости в Linux | `docker exec ... python -m pip check`: `No broken requirements found` |
| Логи | Uvicorn слушает `0.0.0.0:8000`, журнал содержит фактические GET health с 200 |
| Жизненный цикл | `docker stop` дал `exited 0`; `docker rm` удалил учебный контейнер, образ сохранился; контейнер создан повторно |
| Регрессия | 19 pytest-тестов прошли, локальный `pip check` успешен; `npm run validate` проверил 23 операции, 17 таблиц, 23 связи и Markdown-ссылки |
| Независимое ревью | Dockerfile, настройки, команды и документация согласованы; существенных дефектов не обнаружено |

Размер и идентификатор относятся к проверенной локальной сборке. Тег `python:3.13-slim` может обновляться, поэтому будущая сборка может иметь другой размер и ID. При `pip check` от пользователя контейнера pip предупредил о недоступном каталоге кэша; проверка зависимостей прошла. При тестах сохраняется предупреждение Starlette, указанное выше.

Особенность этой Windows-среды: перед сборкой Docker Desktop не запускался из-за недоступных старых Unix-сокетов. При остановленном Desktop каталоги `%LOCALAPPDATA%/Docker/run` и `%LOCALAPPDATA%/docker-secrets-engine` переименованы с суффиксом `.lab4-stale-<дата-время>` и созданы заново; старые каталоги сохранены. Сброс Docker, удаление образов, дисков WSL и томов не выполнялись. Такой обход описан в [трекере Docker Desktop](https://github.com/docker/desktop-feedback/issues/554). После первой успешной проверки контейнера Desktop завершился с ошибкой собственного `com.docker.build`; причина этого завершения не установлена. После повторного запуска Desktop сборка уже находилась локально, а проверки HTTP и полного жизненного цикла контейнера выполнены успешно. При повторении сбоя нужно диагностировать Desktop; успешный ответ health не гарантирует исправность его фоновых служб.

Сборка и запуск проверены реально. Образ не публиковался в реестр. PostgreSQL, Docker Compose и бизнес-операции в лабораторную №4 не включены. Порядок повторения и защиты — в [lab4.md](lab4.md) и [defense-checklist.md](defense-checklist.md).
