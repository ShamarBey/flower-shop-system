# Ответы на контрольные вопросы

## 1. Чем отличается монолитная архитектура от микросервисной?

Монолитная архитектура представляет приложение как единый разворачиваемый процесс. Все модули находятся в одном кодовом репозитории и обычно используют общую базу данных. Ее преимущества для этого проекта — простая разработка, единые транзакции между заказом и складом, небольшой объем инфраструктуры и удобная отладка. Недостатки — масштабирование всего приложения целиком и более сильная связанность модулей.

Микросервисная архитектура разделяет систему на независимые сервисы, например Catalog, Orders и Inventory. Сервисы могут разворачиваться и масштабироваться отдельно, а отказ одного сервиса не обязательно останавливает остальные. Цена — сетевое взаимодействие, распределенные транзакции, отдельный мониторинг, сложная доставка и необходимость согласовывать контракты.

Для учебного проекта выбран модульный монолит. Он сохраняет границы модулей и позволяет позже вынести наиболее нагруженные части в отдельные сервисы, но не добавляет преждевременную инфраструктурную сложность.

## 2. Что такое третья нормальная форма и зачем она нужна?

Третья нормальная форма означает, что таблица уже находится во второй нормальной форме и каждый неключевой атрибут зависит только от ключа, а не от другого неключевого атрибута. Иными словами, в таблице не должно быть транзитивных зависимостей.

В проекте данные товара, категории, склада, пользователя и заказа хранятся в отдельных таблицах. Состав заказа вынесен в `order_items`, состав рецепта — в `recipe_items`, а связь пользователя с ролями — в `user_roles`. Это не дает дублировать названия категорий и товаров в разных строках и уменьшает риск противоречивых обновлений.

Цена и название товара дополнительно копируются в `order_items` как снимок. Это не нарушает смысл модели заказа: снимок нужен для сохранения исторического состояния документа, даже если каталог позже изменится.

## 3. Какую роль выполняет слой бизнес-логики?

Слой бизнес-логики реализует правила предметной области между HTTP API и базой данных. В нашем проекте он проверяет состав букета, совместимость компонентов, допустимые количества, доступный остаток, переходы статусов и правила резервирования.

Контроллер принимает запрос и проверяет формат данных, сервисный слой принимает бизнес-решение, а слой доступа к данным выполняет операции с PostgreSQL. Такое разделение не позволяет перенести правила конструктора только в интерфейс и сохранить корректность при вызове API из другого клиента.

## 4. Зачем нужна C4-модель и чем Container отличается от Component?

C4-модель показывает архитектуру с разных уровней детализации. System Context описывает систему и внешних участников, Container показывает крупные исполняемые части, Component раскрывает внутренние модули контейнера, а Code показывает реализацию отдельных компонентов.

На уровне Container backend, база данных, Redis и внешние уведомления рассматриваются как отдельные технические блоки. На уровне Component внутри Backend API можно показать Auth, Catalog, Bouquet, Order и Inventory. Container не является отдельным классом или файлом: это самостоятельная часть системы, которую можно запустить или заменить как инфраструктурный блок.

## 5. В чем разница между связями 1:N и N:M?

Связь 1:N означает, что одной записи слева соответствует много записей справа. Например, один заказ содержит много строк `order_items`, а один пользователь может иметь много записей истории статусов.

Связь N:M означает, что каждой записи с обеих сторон может соответствовать несколько записей другой стороны. Например, один рецепт содержит много товаров, и один товар может входить в много рецептов. В реляционной базе такая связь реализуется промежуточной таблицей `recipe_items`, где хранятся два внешних ключа и атрибут количества.
