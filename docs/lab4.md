# Лабораторная работа №4 — контейнеризация сервера

Тема: контейнеризация серверного приложения с использованием Docker и написание оптимального Dockerfile.

Предметная область: информационная система управления заказами и товарными запасами цветочного магазина с интерактивным конструктором букетов.

Источник требований — `Lab#04_Docker.pdf`, 5 страниц, из [папки лабораторных работ](https://drive.google.com/drive/folders/1fwY7O8OnPeHtRFqjpxeAQ4JUWXz45qph). Требуются `.dockerignore`, оптимизированный Dockerfile, локальная сборка образа, запуск контейнера с портами и переменными окружения, проверка health-check и ответы на пять контрольных вопросов.

## Область работы

Упаковывается сервер FastAPI из лабораторной №3. В контейнере работает публичный `GET /api/v1/health`; остальные API остаются проектным контрактом. PostgreSQL, миграции, Docker Compose, авторизация и CRUD в эту лабораторную не входят.

Dockerfile разделен на стадии builder и runtime на базе Python 3.13 slim. На стадии сборки устанавливаются закрепленные runtime-зависимости из `requirements.txt` и Python-пакет проекта. В финальную стадию переносится готовое окружение исполнения; тестовые и сборочные инструменты не нужны серверу. Приложение запускается от непривилегированного пользователя с UID `10001`.

Отдельное копирование `requirements.txt` позволяет повторно использовать слой установки зависимостей при изменении только исходного кода. Изменение файла зависимостей инвалидирует этот слой и требует новой установки.

## Контекст сборки и настройки

`.dockerignore` исключает локальные `.env`, `.venv`, `node_modules`, `.git`, тесты, логи и проектную документацию. Они не должны передаваться Docker builder или случайно попадать в слои образа. Само добавление `.env` в `.gitignore` не исключает его из контекста Docker: это разные механизмы.

В образе заданы безопасные настройки исполнения: `HTTP_HOST=0.0.0.0`, `HTTP_PORT=8000`, `APP_ENV=production`. При запуске значения можно переопределить через `docker run -e`. `PYTHONUNBUFFERED` позволяет сразу видеть вывод приложения в `docker logs`.

Файл `.env` не копируется в образ. Для учебной демонстрации ниже настройки передаются явно через `-e`, а не через локальный `.env`: в нем сохранен `HTTP_HOST=127.0.0.1` для запуска без Docker. В контейнере привязка только к его loopback-интерфейсу сделала бы приложение недоступным через опубликованный порт.

## Сборка

Сначала убедитесь, что Docker Engine запущен в режиме Linux-контейнеров. Команды выполняются в PowerShell из корня репозитория:

```powershell
docker info
docker build -t flower-shop-api:lab4 .
docker images flower-shop-api
```

При первой сборке нужен доступ к реестру базового образа и источнику Python-зависимостей. Последующие сборки могут использовать локальный кэш. Результат сборки и фактический размер нужно смотреть в выводе Docker; они не выводятся из одного наличия Dockerfile.

## Запуск и проверка

```powershell
docker run --name flower-shop-lab4 -d -p 127.0.0.1:8081:8000 -e APP_ENV=development -e "APP_NAME=Flower Shop API (Docker)" flower-shop-api:lab4
docker ps --filter name=flower-shop-lab4
curl.exe -i http://127.0.0.1:8081/api/v1/health
docker logs flower-shop-lab4
docker inspect --format '{{.State.Health.Status}}' flower-shop-lab4
```

На компьютере используется порт `8081`, чтобы сохранить локальный backend на `8000` и статический Swagger на `8080`. Сервер внутри контейнера слушает порт `8000`. Публикация `127.0.0.1:8081:8000` разрешает обращаться к нему с этого компьютера.

Ожидаемый ответ содержит `status: pass`, `app_name: Flower Shop API (Docker)`, `version: 1.0.0`, `environment: development` и неотрицательный `uptime`. HTTP-статус — `200 OK`, формат — `application/json`.

Для проверки изнутри контейнера используется Python из образа, поэтому установка curl в runtime не требуется:

```powershell
docker exec flower-shop-lab4 python -c "from urllib.request import urlopen; print(urlopen('http://127.0.0.1:8000/api/v1/health').read().decode())"
```

Встроенный Docker `HEALTHCHECK` также обращается к `/api/v1/health` через стандартную библиотеку Python. Успешная HTTP-проверка переводит статус из `starting` в `healthy`; проверку не нужно путать с подтверждением готовности PostgreSQL или оформления заказа.

Swagger UI контейнерного сервера доступен по адресу `http://127.0.0.1:8081/docs`. Как и локальный интерфейс FastAPI, он загружает ресурсы Swagger из CDN; сам health-check доступа в интернет не требует.

## Жизненный цикл контейнера

Логи и статус показывают, что запущен именно контейнерный экземпляр, а не оставшийся локальный процесс. Перед повторным использованием имени можно проверить `docker ps -a --filter name=flower-shop-lab4`.

```powershell
docker stop flower-shop-lab4
docker rm flower-shop-lab4
```

`docker stop` останавливает процесс, а `docker rm` удаляет остановленный контейнер. Собранный образ сохраняется; его можно запустить командой `docker run` снова. В этой лабораторной контейнер не хранит пользовательские данные.

| Требование | Реализация или действие при сдаче |
|---|---|
| Исключение лишнего из контекста | `.dockerignore` в корне проекта |
| Оптимизированный Dockerfile | Python slim, builder/runtime, кэш зависимостей, непривилегированный пользователь |
| Локальная сборка образа | `docker build -t flower-shop-api:lab4 .`, вывод `docker images` |
| Порты и переменные окружения | `docker run` с `-p` и `-e` |
| Доступный health-check | HTTP 200 на `http://127.0.0.1:8081/api/v1/health` |
| Проверка внутри контейнера | `docker exec` и встроенный `HEALTHCHECK` |
| Управление жизненным циклом | `docker ps`, `docker logs`, `docker stop`, `docker rm` |
| Ответы на вопросы | [control-questions-lab4.md](control-questions-lab4.md) |
